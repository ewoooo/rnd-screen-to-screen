# UXPT_PGT — Page Transition

---

## UXPT_PGT_1 — 전환 방식 결정 기준

> **패턴 태그**: Intent-Based · Frictionless

화면 전환은 고객의 맥락 유지 필요성과 태스크 완결성을 기준으로 설계해야 합니다.

### 전환 방식 선택 기준

| 상황 | 전환 방식 | 기준 |
|------|---------|------|
| 맥락 유지가 필요한 경우 | **바텀시트** | 특정 화면에서 옵션을 선택하면 기존 화면 안에 결과가 반영되어야 하는 부분 태스크 |
| 기존 흐름과 분리되어야 하는 경우 | **팝업(모달)** | 기존 흐름에 방해를 주지 않는 단독 태스크·단일 확인 |
| 정보 구조 변경·단계 전환이 필요한 경우 | **전체 화면 전환** | 정보의 깊이가 확장되거나 새로운 흐름이 시작되는 경우 |

### 규칙

| 규칙 ID | 핵심 제약 | 설명 | 예시 |
|---------|---------|------|------|
| `UXPT_PGT_1_RULE_1` | 맥락 유지 필요 → 바텀시트 | 고객이 보던 정보와 연속성이 유지되어야 하는 부분 태스크에 사용. 설정이 완료되면 기존 화면 안에 결과가 반영되어야 한다. | 요금제 적용 시점 선택, 필터 설정 |
| `UXPT_PGT_1_RULE_2` | 기존 흐름 분리 필요 → 팝업(모달) | 기존 흐름과 완전히 분리되어 집중이 필요한 단계에 사용. | `'결제 완료됐어요'` 단일 확인, 배송지 변경 |
| `UXPT_PGT_1_RULE_3` | 정보 구조 변경·단계 전환 → 전체 화면 전환 | 정보의 깊이가 확장되거나 새로운 흐름이 시작될 때 사용. | 상세 페이지 진입, 청약 단계 진입 |
| `UXPT_PGT_1_RULE_4` | 동일 상황에서 전환 방식 일관성 유지 | 결제 변경 이후 어떤 화면에서는 바텀시트로, 다른 화면에서는 별도 페이지로 처리하는 방식이 달라지면 고객은 화면마다 구조를 새로 이해해야 한다. | 동일 태스크는 항상 동일 전환 방식 적용 |

### Do / Don't

| Do ✅ | Don't ❌ |
|-------|---------|
| 맥락 유지 필요 → 바텀시트 / 분리 필요 → 팝업 / 단계 전환 → 전체 화면 — 상황에 맞는 전환 방식을 일관되게 적용한다. | 동일한 상황에서 화면마다 다른 전환 방식을 적용해 고객이 매번 구조를 재해석하도록 만들지 않는다. |

## UXPT_PGT_2 — 전체 화면 전환

> **패턴 태그**: Frictionless

고객이 새로운 정보 구조로 진입하거나 태스크의 단계가 구조적으로 바뀔 때 사용하는 전환입니다.

### 규칙

| 규칙 ID | 핵심 제약 | 설명 | 예시 |
|---------|---------|------|------|
| `UXPT_PGT_2_RULE_1` | 정보 깊이 확장·새 태스크 시작 시에만 사용 | 옵션 변경이나 필터 적용처럼 선택 결과가 이어지는 태스크를 별도 화면으로 분리하면 불필요한 뒤로 가기 단계가 생긴다. | 상세 진입, 청약·가입 단계 진입 → 전체 화면 / 색상·용량 선택 → 바텀시트 |
| `UXPT_PGT_2_RULE_2` | 전환 시 이전 맥락 뒤로 가기로 복원 가능 | 상세 화면에서 뒤로 가기를 누르면 이전 화면으로 돌아가야 한다. 뒤로 가기가 없거나 홈으로 이동한다면 고객은 이전 경로를 다시 찾아야 한다. | 상세 → 뒤로 가기 → 리스트 (홈으로 이동 금지) |
| `UXPT_PGT_2_RULE_3` | 단계 변화 명확하게 전달 | 고객이 다음 단계로 이동했다는 것을 인지할 수 있어야 한다. 화면 제목, 단계 표시(2/4 등), 구성 변화를 통해 이전 화면과 다른 단계에 진입했음을 명확히 전달해야 한다. | 화면 상단 `'2/4단계'` 표시 |
| `UXPT_PGT_2_RULE_4` | 불필요한 페이지 전환 최소화 | 고객의 이동 단계가 증가하는 불필요한 전환은 최소화해야 한다. 설정 2개를 고르기 위해 별도 화면으로 이동해야 한다면, 해당 설정을 현재 화면의 모달로 처리하여 화면 전환 자체를 없애야 한다. | 색상 선택 → 별도 페이지 분리 금지 → 바텀시트로 처리 |

### Do / Don't

| Do ✅ | Don't ❌ |
|-------|---------|
| **정보 구조가 바뀌는 단계에만 전환** — 화면 구조 자체가 달라지는 단계 진입에서만 전체 화면으로 전환한다. | **단순 항목 변경에 화면 전환** — 단순한 선택을 별도 페이지로 분리하면 고객이 돌아오기 위해 뒤로 가기를 반복해야 한다. |
| `'주문하기'` 단계 진입 → 전체 화면 전환 | `'정렬'` 선택 → 전체 화면 전환 (바텀시트로 처리해야 함) |

## UXPT_PGT_3 — 바텀시트

> **패턴 태그**: Frictionless

현재 화면의 맥락을 유지한 채 선택, 필터, 옵션, 단순한 의사결정을 처리하는 전환입니다.

### 규칙

| 규칙 ID | 핵심 제약 | 설명 | 예시 |
|---------|---------|------|------|
| `UXPT_PGT_3_RULE_1` | 현재 화면 맥락 유지가 필요한 경우에만 사용 | 설정이 완료되면 바텀시트가 닫히고 기존 화면 안에 결과가 반영되어야 한다. | 요금제 적용 시점 선택, 배송 날짜 선택 |
| `UXPT_PGT_3_RULE_2` | 선택·필터·옵션 변경 등 단순 태스크에만 사용 | 정보가 복잡해지는 중요한 내용이나, 단계가 이어지거나 내부 스크롤이 필요한 수준이면 전체 화면 전환을 사용해야 한다. | 단순 정렬 선택 → 바텀시트 / 복잡한 약관 동의 → 전체 화면 |
| `UXPT_PGT_3_RULE_3` | 기존 화면은 어둡게 처리해 시각적 분리·유지 | 현재 태스크와 기존 화면을 명확히 구분해야 하지만, 어느 화면 안에서 선택 중인지 인지할 수 있어야 한다. 바텀시트가 올라오면 배경 화면이 어둡게 처리되어 고객은 어디서 선택 중인지 맥락을 유지한다. | 배경 dimming 처리 필수 |
| `UXPT_PGT_3_RULE_4` | 닫으면 기존 화면 상태 즉시 그대로 복원 | 닫은 이후 고객이 다시 이전 화면을 탐색하거나 스크롤해서 돌아가야 하는 상황이 생기지 않아야 한다. | 바텀시트 닫기 → 기존 화면 스크롤 위치·상태 복원 |

### Do / Don't

| Do ✅ | Don't ❌ |
|-------|---------|
| **단순한 선택이 이뤄지는 바텀시트** — 하나의 선택으로 바로 완결되는 바텀시트로, 고객이 맥락을 유지한 채 즉시 결과를 확인한다. | **시트 안에서 단계가 이어지는 구조** — 선택 후 `'다음'`으로 다음 단계가 이어지는 구조. 바텀시트는 단일 결정으로 완결되어야 한다. |
| 정렬 선택 → 선택 즉시 바텀시트 닫힘 + 결과 반영 | 정렬 선택 → `'다음'` 버튼 → 추가 단계 진입 |

### 시나리오 — 상황별 적용 방식

| 시나리오 | 바텀시트 내용 | 완결 조건 |
|----------|------------|---------|
| 요금제 적용 시점 선택 | `'다음 달 1일부터 적용'` / `'오늘부터 바로 적용'` / `'변경 날짜 직접 선택'` | 선택 즉시 닫힘 + 요금제 비교 화면에 결과 반영 |
| 데이터 요청 용량 선택 | 1GB / AI 추천 / 직접 입력 | 선택 즉시 닫힘 + 잔여량 화면에 반영 |

## UXPT_PGT_4 — 팝업(모달)

> **패턴 태그**: Frictionless

현재 흐름을 일시적으로 중단하고, 기존 흐름과 분리된 태스크를 집중적으로 처리하게 하는 전환입니다.

### 규칙

| 규칙 ID | 핵심 제약 | 설명 | 예시 |
|---------|---------|------|------|
| `UXPT_PGT_4_RULE_1` | 기존 흐름과 완전히 분리된 단독 태스크에만 사용 | 이탈이 필요하거나 여러 화면을 오가야 하는 태스크에 팝업을 사용하면 경험이 단절되어 고객이 현재 어느 구조에 있는지 파악할 수 없다. | `'결제 완료됐어요'` 단일 확인, 배송지 변경 |
| `UXPT_PGT_4_RULE_2` | 팝업 안에서 태스크 완결 | 팝업에서 버튼을 눌렀을 때 다음 이동이 일어나거나 전체 화면으로 전환되면, 고객은 현재 어느 구조에 있는지 파악할 수 없게 된다. | 배송지 변경 → 팝업 안에서 선택·확인 완결 |
| `UXPT_PGT_4_RULE_3` | 종료는 닫기를 통해서만 | 단순 확인·선택은 닫기만으로 완료되며, 뒤로 가기는 존재하지 않는다. 단, 팝업 안에 여러 단계가 있는 프로세스에서는 선택적으로 뒤로 가기와 닫기를 모두 사용할 수 있다. | 닫기 1개만 표시 — 뒤로 가기 + 닫기 동시 표시 금지 (단계 없는 팝업) |
| `UXPT_PGT_4_RULE_4` | 작성·입력 상태 팝업에서 닫기 전 저장 여부 확인 필수 | 확인 없이 닫히면 고객은 내용을 잃고 처음부터 다시 해야 하므로, 닫기 클릭 시 작성 중인 내용이 사라지는 것에 대한 확인이 필요하다. | `'닫으면 입력 중인 내용이 사라져요. 그래도 닫으시겠어요?'` |

### Do / Don't

| Do ✅ | Don't ❌ |
|-------|---------|
| **단순 팝업 내 태스크 완결** — 독립 태스크가 팝업 안에서 시작되고 완결된다. 닫기만 표시되어 종료 방법이 하나로 명확하다. | **단순 팝업 내 화면 이동** — 단순 확인·선택 팝업 내 뒤로 가기와 닫기가 동시에 있으면, 각 버튼이 어디로 이동하는지 예측할 수 없다. |
| 배송지 변경 팝업: 선택 완결 + 닫기만 표시 | 배송지 변경 팝업: 뒤로 가기 + 닫기 동시 노출 |

### 시나리오 — 상황별 적용 방식

| 시나리오 | 전환 방식 | 완결 조건 |
|----------|---------|---------|
| 결제 완료 안내 | 팝업(모달) | 닫기 버튼만 표시 → 클릭 시 기존 화면 복귀 |
| 배송지 변경 | 팝업(모달) | 팝업 안에서 주소 선택 완결 → 닫기 시 기존 주문 화면에 반영 |
| 약관 상세 보기 (단순 확인) | 팝업(모달) | 내용 확인 후 닫기만으로 완료 — 뒤로 가기 없음 |
| 주문서 작성 중 닫기 시도 | 팝업(모달) — 저장 여부 확인 | `'닫으면 입력 중인 내용이 사라져요. 그래도 닫으시겠어요?'` → 계속 작성 / 닫기 |
