# Tailwind Migration

## Purpose

This document defines how `@pxds/cx-tokens` should support Tailwind without weakening the token source of truth.

The goal is not to replace CX tokens with Tailwind defaults. Tailwind should become a thin utility syntax over CX token aliases so component styles can move closer to `cva` variant definitions while preserving the existing design system contract.

## Current Source Of Truth

`src/tokens.css` is generated from the Tokens Studio source under `src/originals`.

Do not hand-edit token values in generated CSS.

```txt
src/originals
  -> scripts/generate-css-variables.mjs
  -> src/tokens.css
```

The generated file currently contains:

- Primitive tokens: `--color-*`, `--spacing-*`, `--radius-*`, font primitives.
- Text style tokens: `--16-semi-*`, `--14-med-*`, etc.
- Light and dark semantic tokens: `--semantic-light-*`, `--semantic-dark-*`.
- Light and dark component tokens: `--component-light-*`, `--component-dark-*`.

Tailwind must consume these tokens. It must not define a competing palette, spacing scale, radius scale, or typography scale.

## Migration Principle

Tailwind should also have a three-layer structure, matching the intent of `tokens.css` without copying token values into component code.

```txt
src/tokens.css
  -> src/tailwind/aliases.css
  -> src/tailwind/tailwind.css
  -> src/tailwind/style.css
  -> cva component variants
```

The important distinction:

- `tokens.css` keeps exact generated values.
- `tailwind/aliases.css` decides which light or dark semantic/component token is active.
- `tailwind/tailwind.css` exposes those aliases as readable utility names.
- `tailwind/style.css` is the public adapter imported by consumers.
- Components use the generated utility classes through `cva`.

Do not treat Tailwind as a new token source. Treat it as a utility adapter over the CX token source.

## Tailwind Token Layers

Use these files:

```txt
packages/cx-tokens/src/tokens.css
packages/cx-tokens/src/tailwind/aliases.css
packages/cx-tokens/src/tailwind/tailwind.css
packages/cx-tokens/src/tailwind/style.css
```

### 1. Generated Tokens

`tokens.css` remains the source of generated token values.

It owns:

- Primitive values: `--color-blue-500`, `--spacing-16`, `--radius-r3`.
- Text style values: `--16-semi-font-size`, `--14-med-line-height`.
- Theme-specific semantic tokens: `--semantic-light-*`, `--semantic-dark-*`.
- Theme-specific component tokens: `--component-light-*`, `--component-dark-*`.

This file is generated. Do not hand-edit it.

### 2. Theme-Neutral Aliases

Tailwind classes should not need to know whether a token is light or dark.

Add `tailwind/aliases.css` outside the generated token value block. These aliases may be generated by a companion script or maintained as a small handwritten file, but they should not overwrite the primitive token source.

Example:

```css
:root,
[data-theme="light"] {
	--semantic-color-text-primary: var(--semantic-light-color-text-primary);
	--semantic-color-bg-default: var(--semantic-light-color-bg-default);
	--semantic-color-border-subtle: var(--semantic-light-color-border-subtle);

	--component-button-bg-primary: var(--component-light-button-bg-primary);
	--component-button-bg-secondary: var(--component-light-button-bg-secondary);
	--component-button-bg-disabled: var(--component-light-button-bg-primary-disabled);
	--component-button-fg-primary: var(--component-light-button-fg-primary);
	--component-button-fg-secondary: var(--component-light-button-fg-secondary);
	--component-button-fg-disabled: var(--component-light-button-fg-primary-disabled);
	--component-button-border-secondary: var(--component-light-button-border-secondary);
}

[data-theme="dark"] {
	--semantic-color-text-primary: var(--semantic-dark-color-text-primary);
	--semantic-color-bg-default: var(--semantic-dark-color-bg-default);
	--semantic-color-border-subtle: var(--semantic-dark-color-border-subtle);

	--component-button-bg-primary: var(--component-dark-button-bg-primary);
	--component-button-bg-secondary: var(--component-dark-button-bg-secondary);
	--component-button-bg-disabled: var(--component-dark-button-bg-primary-disabled);
	--component-button-fg-primary: var(--component-dark-button-fg-primary);
	--component-button-fg-secondary: var(--component-dark-button-fg-secondary);
	--component-button-fg-disabled: var(--component-dark-button-fg-primary-disabled);
	--component-button-border-secondary: var(--component-dark-button-border-secondary);
}
```

With this model, component classes stay stable:

```tsx
"bg-button-secondary text-button-fg-secondary"
```

Theme changes are handled by CSS variable values, not by duplicating every class with `dark:`.

### 3. Tailwind Theme Exposure

For Tailwind v4, prefer a CSS-first theme file that maps Tailwind theme variables to CX aliases.

The Tailwind exposure must preserve all three token layers:

```txt
primitive  -> --radius-r0, --font-size-10
semantic   -> --semantic-light-color-border-strong-rgb
semantic   -> --semantic-dark-color-border-strong-rgb
alias      -> --semantic-color-border-strong-rgb
component  -> --component-light-button-bg-secondary
component  -> --component-dark-button-bg-secondary
alias      -> --component-button-bg-secondary
```

The readable token key is the CSS custom property name without `--`.

```txt
--radius-r0 -> radius-r0
--font-size-10 -> font-size-10
--semantic-color-border-strong-rgb -> semantic-color-border-strong-rgb
```

For property-specific utility classes, Tailwind still applies its normal namespace:

```txt
--radius-r0 -> rounded-r0
--font-size-10 -> text-10
--semantic-color-border-strong -> border-[var(--semantic-color-border-strong)]
```

Use `semantic`, not `sementic`, to match the existing token path.

In addition to exact token keys, `generate-tailwind.mjs` may emit Tailwind color namespace aliases for component ergonomics:

```txt
--semantic-color-text-primary -> --color-text-primary -> text-text-primary
--component-button-bg-secondary -> --color-button-secondary -> bg-button-secondary
--component-button-border-secondary -> --color-button-border-secondary -> border-button-border-secondary
```

These aliases are convenience utility contracts. They do not replace the exact token-key exposure.

Example target file:

```txt
packages/cx-tokens/src/tailwind/tailwind.css
```

Example:

```css
@theme {
	--semantic-light-color-border-strong-rgb: <generated from tokens.css>;
	--semantic-dark-color-border-strong-rgb: <generated from tokens.css>;
	--semantic-color-border-strong-rgb: var(--semantic-light-color-border-strong-rgb);

	--component-light-button-bg-secondary: <generated from tokens.css>;
	--component-dark-button-bg-secondary: <generated from tokens.css>;
	--component-button-bg-secondary: var(--component-light-button-bg-secondary);
	--color-button-secondary: var(--component-button-bg-secondary);

	/*
	 * Spacing and radius already use Tailwind-compatible names in the token
	 * source. Emit them into @theme from the generator instead of writing
	 * recursive aliases such as `--spacing-16: var(--spacing-16)`.
	 */
	--spacing-16: <generated from tokens.css>;
	--radius-r3: <generated from tokens.css>;
}
```

Text styles must also be expressible as Tailwind utilities. Existing text style classes should be emitted through Tailwind `@utility` using the same class contract:

```css
@utility text-20-med {
	font-family: var(--20-med-font-family);
	font-weight: var(--20-med-font-weight);
	line-height: var(--20-med-line-height);
	font-size: var(--20-med-font-size);
	letter-spacing: var(--20-med-letter-spacing);
}
```

This keeps the migration path stable:

```txt
.text-20-med -> text-20-med
```

Expose the Tailwind adapter through a public `style.css` file:

```txt
packages/cx-tokens/src/tailwind/style.css
```

Example:

```css
@import "tailwindcss";
@import "./tailwind.css";
@import "../tokens.css";
@import "./aliases.css";
```

Consumers should import `style.css`, not `aliases.css` or `tailwind.css` directly. This keeps the Tailwind implementation isolated under `src/tailwind` and leaves room to change the internal split later.

Package exports should expose only the public adapter:

```json
{
	"sideEffects": [
		"./src/tokens.css",
		"./src/text-styles.css",
		"./src/tailwind/style.css"
	],
	"exports": {
		"./tokens.css": "./src/tokens.css",
		"./tailwind/style.css": "./src/tailwind/style.css"
	}
}
```

The migration target import should become:

```css
@import "@pxds/cx-tokens/tailwind/style.css";
```

Existing `@pxds/cx-tokens/tokens.css` imports can remain during the transition, but Tailwind-enabled consumers should move to the adapter once it exists.

Then component code can use token-backed utilities without a project prefix:

```tsx
"bg-button-secondary text-button-fg-secondary border-button-border-secondary px-16 rounded-r3"
```

For Tailwind v3, provide an equivalent preset that maps values to the same CSS variable aliases. The class naming should match the v4 names as closely as possible.

Do not use a `cx-*` prefix for Tailwind utility names. The token ownership should be enforced by the Tailwind theme source and review checklist, not by verbose class names.

When a Tailwind theme variable has the same name as an existing token variable, do not alias it to itself. Either emit the theme variable directly from the token generator or keep using an arbitrary CSS variable class until the generator supports it.

## Dark Theme Strategy

Prefer variable swapping over heavy `dark:` class usage.

Recommended:

```tsx
"bg-button-secondary text-button-fg-secondary"
```

Avoid:

```tsx
"bg-button-secondary dark:bg-button-secondary-dark"
```

Use `dark:` only when the component structure or behavior changes between themes. Color changes should normally be handled by aliases.

If Tailwind dark variants are needed, configure them to follow the existing project convention:

```css
@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));
```

## Component Migration Pattern

Components should continue to use `cva` and `cn`.

Before:

```ts
export const buttonVariants = cva("cx-button", {
	variants: {
		variant: {
			primary: "cx-button--primary",
			secondary: "cx-button--secondary",
		},
	},
});
```

After:

```ts
export const buttonVariants = cva(
	[
		"inline-flex items-center justify-center",
		"box-border appearance-none whitespace-nowrap",
		"font-semibold leading-[1.3] tracking-normal",
		"transition-colors",
		"focus-visible:outline focus-visible:outline-2",
	].join(" "),
	{
		variants: {
			variant: {
				primary: "bg-button-primary text-button-fg-primary",
				secondary:
					"bg-button-secondary text-button-fg-secondary border border-button-border-secondary",
				disabled:
					"bg-button-disabled text-button-fg-disabled pointer-events-none cursor-not-allowed",
			},
			size: {
				small: "min-h-8 px-12 text-[length:var(--12-semi-font-size)] rounded-full",
				medium: "min-h-10 px-16 text-[length:var(--14-semi-font-size)] rounded-r3",
			},
		},
	}
);
```

The example still uses text-style variables directly where Tailwind utility naming would become too noisy. That is acceptable while typography aliases are being designed.

## Documentation Impact

After migration, component documents should stop listing long CSS implementation details. They should instead document:

- Component purpose.
- Props and variants.
- Figma mapping props.
- Component dependencies.
- Accessibility and state rules.
- The `cva` variant file as the styling source.

Style values should live in token aliases and `cva` definitions, not in prose.

## Rollout Order

Start with components whose visual state is mostly variant-driven.

Recommended first pass:

1. Keep `tokens.css` as the generated source.
2. Run `npm run generate:css -w @pxds/cx-tokens` after Tokens Studio source changes.
3. Run `npm run generate:tailwind -w @pxds/cx-tokens` to create `src/tailwind/aliases.css`, `src/tailwind/tailwind.css`, and `src/tailwind/style.css`.
4. Convert `Button` as the pilot.
5. Convert simple primitives:
   - `Badge`
   - `ChipItem`
   - `TabItem`
   - `ButtonTextUnderline`
   - `ButtonXsmallSolid`
6. Convert compounds only after the primitive pattern is stable.

Avoid starting with `TextField`, `TitleSection`, or list components because they mix internal slots, layout, and state more heavily.

## Validation Checklist

For every Tailwind migration PR:

- No raw Tailwind default colors like `bg-blue-500`, `text-gray-900`, or `rounded-lg`.
- No new raw spacing or radius values unless documented as a token gap.
- Classes must use token-backed utility names such as `bg-button-secondary`, `px-16`, and `rounded-r3`, or explicit CSS variable arbitrary values.
- Do not introduce the `cx-*` prefix in Tailwind utility names.
- `tokens.css` generated values must not be hand-edited.
- `tailwind/aliases.css` must only map existing generated tokens to theme-neutral names.
- `tailwind/tailwind.css` must only expose generated tokens or aliases to Tailwind theme variables.
- Consumers must import `tailwind/style.css`, not the internal Tailwind files directly.
- Light and dark themes must be verified through variable swapping.
- Component bridge attributes must remain unchanged.
- Run the relevant consumer checks:

```sh
npm run lint -w @screen/mobile
npm run build -w @screen/mobile
```

## Open Decisions

- Whether Tailwind v4 is the migration target now, or whether a v3-compatible preset is needed first.
- Whether `tailwind/aliases.css` should be generated by `scripts/generate-tailwind.mjs` or maintained in a separate handwritten file.
- Whether `tailwind/tailwind.css` should be generated with token values for spacing/radius to avoid same-name recursive aliases.
- Exact naming convention for color utilities:
  - Semantic colors: `text-primary`, `bg-default`, `border-subtle`
  - Component colors: `bg-button-secondary`, `text-button-fg-secondary`, `border-button-border-secondary`
  - Avoid project prefixes such as `cx-*`
- Typography utility strategy for named text styles such as `12 semi`, `14 semi`, and `16 semi`.
- Whether component package CSS files should be fully removed or reduced to rare structural selectors only.
